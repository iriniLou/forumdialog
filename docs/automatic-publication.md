# Автоматическая публикация: доступ и реальные ограничения

Исходники: https://github.com/iriniLou/forumdialog . Облачная база и сайт не считаются готовыми, пока workflow не проверит их по сети. Локальная проверка не заменяет этот этап.

Единственное недостающее действие владельца для запуска подготовленной автоматизации — сохранить **Supabase personal access token** как GitHub Actions repository secret с именем `SUPABASE_ACCESS_TOKEN`:

- Создание токена в своём аккаунте Supabase: https://supabase.com/dashboard/account/tokens . Не отправлять токен в чат.
- Защищённая форма секрета нужного репозитория: https://github.com/iriniLou/forumdialog/settings/secrets/actions/new . Name: `SUPABASE_ACCESS_TOKEN`, Secret: созданный токен, затем Add secret.

Это доступ к управлению ресурсами аккаунта Supabase. Токен хранится только в GitHub Secrets; его можно отозвать на странице токенов. Не используйте service_role вместо management token. При отсутствии аккаунта потребуется сначала войти/зарегистрироваться в Supabase; автоматизация не создаёт учётные записи пользователей внешнего сервиса и не принимает условия от их имени.

После добавления секрета запланированный workflow обнаружит его (расписание раз в 15 минут; GitHub может запускать его с задержкой). При желании запуск доступен через Run workflow на https://github.com/iriniLou/forumdialog/actions/workflows/publish.yml . Добавление секрета не является доказательством успешного запуска.

Что подготовленный workflow должен выполнить после разрешения доступа:

1. Проверить модель, SQL, сборку и браузерные сценарии.
2. Создать выделенную организацию `forumdialog-<repository id>` и проект Supabase в EMEA с минимальными стандартными ресурсами. Новая организация создаётся с настройками сервиса по умолчанию (обычно Free); API не вызывает покупку, смену тарифа или включение платных опций. При отказе по квоте остановится. Платный тариф автоматически не подключается.
3. Повторно использовать свой проект по точному имени и организации. Не трогать посторонние проекты и события. Если обнаружено неоднозначное существующее событие или несколько владельцев — остановиться для проверки, не угадывать.
4. Применить схему и пустой сценарий; включить анонимные сессии, настроить безопасные redirect URL. Оставить service_role только внутри runner, проверить его отсутствие в клиентском bundle.
5. Пригласить единственного владельца созданной организации в защищённую панель письмом, без публикации пароля.
6. Проверить по сети 350 сессий/отправок за 25 секунд, чтение безопасных данных, модерацию и запреты доступа. Тестовые событие и учётные записи удалить. При отказе публикация не продолжится.
7. Включить GitHub Pages с HTTPS и опубликовать приложение. Чистые маршруты под `/forumdialog/` поддерживаются специальной 404-страницей; токены входа остаются во fragment, не переносятся в query string.
8. Открыть опубликованные интерфейсы браузером: отправка с телефона, вход модератора с отдельной временной тестовой учётной записью, ручной ввод, одобрение, скрытие, XLSX. Удалить тестовые данные.
9. Только после успешной проверки создать архив ссылок и QR. Следующие push в main автоматически обновят сайт. Успешно проверенная версия повторно по расписанию не тестируется; новая версия — да.

Подготовка этого workflow не означает, что пункты 2–9 выполнены: в текущей облачной сессии нет Supabase management token, локальный доступ к GitHub API запрещён сетевой политикой. Git чтение/запись работают и проверены отдельно. Workflow использует собственный GitHub runner; его сеть не зависит от сетевых правил этой среды.

Возможные внешние ограничения: квота бесплатных проектов, необходимость первоначальной активации GitHub Actions/Pages владельцем, отсутствие доступа к Secrets, лимиты почты Supabase, лимиты Auth на один IP, недоступность региона, условия тарифов. Ни одно из них нельзя обойти публикацией демо или хранением ответов в браузере. Если реальный запуск встретит такой отказ, нужны его конкретные результаты; здесь они не выдумываются.

Проверка 350 запросов с одного runner измеряет сервер и HTTP, но не гарантирует Wi-Fi зала. Перед мероприятием нужен прогон с реальными телефонами. Автоматическая первичная настройка не назначает срок удаления: срок хранения согласуется отдельно.
